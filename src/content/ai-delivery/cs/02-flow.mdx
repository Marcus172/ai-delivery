<Detail locale={locale}>

Jádrem flow je **generický kontrakt**: pořadí kroků, sedm invariantů (každý vznikl po skutečném incidentu), pravidla, jak se vrstvy rozlišují, a&nbsp;číslo verze s&nbsp;migračními poznámkami. Skilly, které vývojáři skutečně spouštějí, jsou tenké vstupní body; logika žije pod nimi.

Každý kus logiky pak musel odpovědět na jednu otázku: *liší se to mezi dvěma skutečnými repozitáři?* Odpověď ho zařadila do jedné ze tří dalších vrstev.

**Klientský preset** implementuje capabilities, které kontrakt pojmenovává, pro tracker, hosting a&nbsp;release model daného klienta: najdi pracovní položku, zvol režim triáže, urči cílové release linie, otevři pull request, zamerguj změnu, posuň stav položky. **Vrstva repozitáře** přidává těch pár procedur, které jsou vlastností kódu, třeba jeho quality gate a&nbsp;způsob, jak se zakládá pracoviště. **Osobní vrstva** se nikdy necommituje; drží volbu nástrojů každého vývojáře za uzavřeným seznamem bodů rozšíření a&nbsp;k&nbsp;tomu preference jako modely nebo umístění na stroje.

Jedna asymetrie je záměrná: poskytovatel checkoutu má týmový default v&nbsp;repozitáři, jediný osobní soubor ho přebije a&nbsp;po jeho smazání se default vrátí. Bez defaultu by nový člen týmu tiše pracoval v&nbsp;checkoutu orchestrátoru.

<Note>
  <strong>Verzovaný kontrakt a&nbsp;doctor.</strong> Každý běh porovná verzi profilu repozitáře s&nbsp;verzí pluginu. Při neshodě vypíše jeden řádek varování a&nbsp;pokračuje; nikdy nespadne. Diagnostický příkaz ukáže sloučenou konfiguraci s&nbsp;původem každé hodnoty, kde se který bod rozšíření rozlišil, a&nbsp;suchý běh resolverů. Pravidlo za verzováním: osobní kopie procedury, která pořád učí zrušený krok, je horší než chybějící soubor.
</Note>
