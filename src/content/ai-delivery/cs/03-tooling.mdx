<Detail locale={locale}>

Kontrakt jmenuje **operace**, ne nástroje: kde jsem, kdo je online, založ pracoviště, spusť v&nbsp;něm příkaz, doruč agentovi brief, co běží, archivuj. Každý vývojář tyhle operace implementuje v&nbsp;osobní vrstvě tím, co mu vyhovuje. Nad jedním repozitářem dnes jeden vývojář jede na Paseu, druhý na worktrunku s&nbsp;přímou session a&nbsp;třetí nepoužívá nic a&nbsp;pracuje na místě.

Kontrakt drží od sebe dvě osy: kde vzniká pracovní kopie a&nbsp;kam padá brief pro agenta. Nástroje na pracoviště je pokrývají v&nbsp;různých kombinacích; nástroj, který pokrývá obě, si předá neprůhledný handle sám sobě. Právě to oddělení drží jména nástrojů mimo generickou vrstvu.

Výměna nástroje mění jen soubory osobní vrstvy: poskytovatele flotily, poskytovatele checkoutu, UI pracoviště, preference. Všechno ostatní (git replika stavu, profil dotfiles, ssh, worktree hooky, orchestrační smyčka, plan app, privátní síť) na nástroji nezávisí a&nbsp;výměnu přežije beze změny.

Moje vlastní osobní vrstva běží na Paseu: zdarma, end-to-end relay, příkazová řádka na všechno, daemon jako služba, mobilní aplikace. Delivery flow umožnilo pracovat na mnoha úlohách paralelně a&nbsp;naplno využít rozpočet tokenů, a&nbsp;proto sahá přes flotilu výše.

### Flotila v&nbsp;kontraktu

Flotila přišla do kontraktu jako dva další body rozšíření, ne jako nástroj. **Poskytovatel flotily** odpovídá, kdo je online, založí pracoviště na zvoleném stroji a&nbsp;spustí v&nbsp;něm příkaz; **úložiště stavu** říká, kde žije stav práce. Každý krok, který rozjíždí práci, přijímá cílový stroj, takže tiket jde spustit z&nbsp;notebooku a&nbsp;nechat běžet na desktopu. Bez té vrstvy se flow chová přesně jako na jednom stroji.

Pár pravidel vzešlo ze selhání, ne z&nbsp;návrhu:

- **Offline stroj je stop.** Převzetí práce jiným strojem je výslovná volba, nikdy tichý přesun.
- **Žádná práce dvakrát.** Než vznikne pracoviště, zkontrolují se po pořadě tři zdroje: úložiště stavu, vlastní registr nástroje a&nbsp;větev, která se pushne hned, jak pracoviště existuje.
- **Vzdálený shell je nouzový nástroj, ne transport.** Orchestrace (pracoviště, spuštění agenta, doručení briefu) jde přes control plane nástroje; kopírování souborů a&nbsp;spouštění příkazů jde přes ssh, s&nbsp;kontrolními součty a&nbsp;návratovými kódy, protože vlastní doručování kláves v&nbsp;nástroji se ukázalo jako nespolehlivé.

### Stav práce: git replika a&nbsp;ledgery

Všechno, co flow o&nbsp;práci ví, jsou obyčejné soubory v&nbsp;jednom git repozitáři, replikovaném na každý stroj: meta tiketů, strojově kontrolovatelná kritéria, která dokazují červenou před zelenou, paměť, mapy rozhodnutí a&nbsp;research. Dva druhy souborů brání tomu, aby se dva stroje přetahovaly:

- **Meta** je jeden JSON soubor na tiket. Vlastní merge driver ho slučuje po klíčích, takže do něj může psát orchestrátor na jednom stroji i&nbsp;agent na druhém. Sloučení zastaví jen stejné pole se dvěma různými hodnotami, protože to znamená, že stejná práce běží dvakrát.
- **Ledgery** jsou průběžné záznamy, které si orchestrační smyčka vede, aby se neopakovala: které pull requesty prošly review a&nbsp;na kterém commitu, které opravy už jsou zkontrolované proti každé novější release linii, které tikety už ukázal ranní briefing. Každý stroj píše jen do vlastního souboru ledgeru a&nbsp;smyčka čte jejich sjednocení, takže ledgery nekonfliktují vůbec.

### Konfigurace: profil v&nbsp;chezmoi

chezmoi spravuje dotfiles z&nbsp;git repozitáře. Můj profil drží všechno, co stroj potřebuje, aby se k&nbsp;flotile připojil: nastavení shellu, osobní vrstvu flow, nastavení agentů, hooky a&nbsp;osobní skilly, služby, které drží daemony v&nbsp;chodu, a&nbsp;tajemství šifrovaná přes age. Je pull-based: každý stroj si profil aplikuje z&nbsp;gitu a&nbsp;žádný stroj není ten, kde se konfigurace píše. Nový stroj se připojí přes řízený setup skill a&nbsp;doctor na každém stroji projde zhruba dvacet kontrol (verze, ssh oběma směry, porty, keychain, profil, pluginy), u&nbsp;každého červeného řádku s&nbsp;přesným krokem opravy.

### Když dochází paměť

S&nbsp;výchozím nastavením služby jednou nedostatek paměti zastavil celý daemon agentů se všemi agenty v&nbsp;něm. Dnes služba při tlaku na paměť běží dál, správce paměti pozastaví nejmladší dávkovou úlohu (běh testů, typecheck, nikdy session agenta), dokud se paměť neuvolní, a&nbsp;obal pro opakování zopakuje úlohu jen tehdy, když umřela na paměť, nikdy když test opravdu selhal.
