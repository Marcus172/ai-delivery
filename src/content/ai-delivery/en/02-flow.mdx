<Detail locale={locale}>

At the core of the flow is a **generic contract**: the order of steps, seven invariants (each one written after a real incident), the rules for how the layers resolve, and a version number with migration notes. The skills that developers actually invoke are thin entry points; the logic lives underneath.

Every piece of logic then had to answer one question: *does this differ between two real repositories?* The answer sorted it into one of three further layers.

The **client preset** implements the capabilities the contract names, for that client's tracker, hosting and release model: resolve a work item, pick a triage mode, resolve target release lines, open a pull request, land a change, advance the work item. The **repository layer** adds the few procedures that are a property of the codebase, such as its quality gate and how a workspace is provisioned. The **personal layer** is never committed; it holds each developer's choice of tools behind a closed list of extension points, plus preferences such as models and machine placement.

One asymmetry is deliberate: the checkout provider has a team default in the repository, a single personal file overrides it, and deleting that file brings the default back. Without the default a new team member would silently work inside the orchestrator's own checkout.

<Note>
  <strong>A versioned contract and a doctor.</strong> Each run compares the repository's profile version with the plugin's. On a mismatch it prints one warning line and continues; it never fails. A diagnostics command shows the merged configuration with the origin of every value, where each extension point resolved, and a dry run of the resolvers. The rule behind the versioning: a personal copy of a procedure that still teaches a cancelled step is worse than a missing file.
</Note>
