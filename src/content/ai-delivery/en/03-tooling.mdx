<Detail locale={locale}>

The contract names **operations**, not tools: where am I, who is online, create a workspace, run a command there, deliver a brief to an agent, what is running, archive. Each developer implements those operations in the personal layer with whatever they prefer. On one repository today, one developer runs Paseo, another runs worktrunk with a direct session, and a third uses nothing at all and works in place.

The contract keeps two axes apart: where the working copy is created, and where the brief for the agent lands. Workspace tools cover them in different combinations; a tool that covers both hands itself an opaque handle. That separation is what keeps every tool name out of the generic layer.

Swapping a tool changes only files of the personal layer: the fleet provider, the checkout provider, the workspace UI, the preferences. Everything else (the git state replica, the dotfiles profile, ssh, the worktree hooks, the orchestration loop, the plan app, the private network) does not depend on the tool and survives a swap untouched.

My own personal layer runs on Paseo: free, an end-to-end relay, a command line for everything, a daemon as a service, a mobile app. The delivery flow made it possible to work on many tasks in parallel and to use the token budget to the full, which is why it spans the fleet above.

### The fleet in the contract

The fleet came into the contract as two more extension points, not as a tool. The **fleet provider** answers who is online, creates a workspace on a given machine and runs a command there; the **state store** says where the state of the work lives. Every step that starts work takes a target machine, so a ticket can be started from the laptop and run on the desktop. Without the layer the flow behaves exactly as on one machine.

A few rules came from failures, not from design:

- **An offline machine is a stop.** Taking work over to another machine is an explicit choice, never a silent move.
- **No duplicate work.** Before a workspace is created, three sources are checked in order: the state store, the tool's own registry, and the branch, which is pushed the moment the workspace exists.
- **A remote shell is an emergency tool, not the transport.** Orchestration (workspaces, starting an agent, delivering the brief) goes through the tool's control plane; copying files and running commands go over ssh, with checksums and exit codes, because the tool's own keystroke delivery turned out to be unreliable.

### State of the work: a git replica and ledgers

Everything the flow knows about the work is plain files in one git repository, replicated to every machine: ticket metadata, the machine-checkable criteria that prove red before green, memory, decision maps and research notes. Two kinds of file keep two machines from fighting:

- **Metadata** is one JSON file per ticket. A custom merge driver merges it key by key, so an orchestrator on one machine and an agent on the other can both write to it. Only the same field with two different values stops the merge, because that means the same work is running twice.
- **Ledgers** are running records the orchestration loop keeps so it never repeats itself: which pull requests were reviewed at which commit, which fixes have already been checked against every newer release line, which tickets the morning briefing has already shown. Each machine writes only its own ledger file and the loop reads the union, so ledgers never conflict at all.

### Configuration: a chezmoi profile

chezmoi manages dotfiles from a git repository. My profile holds everything a machine needs to join: the shell setup, the personal layer of the flow, the agent settings, hooks and personal skills, the services that keep the daemons running, and the secrets, encrypted with age. It is pull-based: every machine applies the profile from git, and no machine is the one where configuration is written. A new machine joins through a guided setup skill, and a doctor runs about twenty checks per machine (versions, ssh in both directions, ports, keychain, profile, plugins), each failing line with the exact step that fixes it.

### When memory runs short

Under the default service settings, running out of memory once stopped the whole agent daemon with every agent in it. Now the service keeps running on memory pressure, a governor pauses the youngest batch job (a test run, a type-check, never an agent session) until memory frees up, and a retry wrapper repeats a job only when it died of memory, never when a test really failed.
