The contract names **operations**, not tools: where am I, who is online, create a workspace, run a command there, deliver a brief to an agent, what is running, archive. Each developer implements those operations in the personal layer with whatever they prefer. On one repository today, one developer runs Paseo, another runs worktrunk with a direct session, and a third uses nothing at all and works in place. Three tools, one process.

The contract keeps two axes apart: where the working copy is created, and where the brief for the agent lands. Workspace tools cover them in different combinations; a tool that covers both hands itself an opaque handle. That separation is what keeps every tool name out of the generic layer.

### What a swap touches

Swapping a tool changes only files of the personal layer: the fleet provider, the checkout provider, the workspace UI, the preferences. The contract and the team's configuration in the repository stay as they are. Everything else (the git state replica, the dotfiles profile, ssh, the worktree hooks, the orchestration loop, the plan app, the private network) does not depend on the tool and survives a swap untouched.

My own personal layer runs on Paseo: free, an end-to-end relay, a command line for everything, a daemon as a service, a mobile app.

### The fleet

The delivery flow made it possible to work on many tasks in parallel and to use the token budget to the full (token maxxing). With that, the bottleneck moved from tokens to hardware: RAM and CPU for what the agents actually run, such as end-to-end tests, the monorepo's build and type-check, and long-running research agents. So my personal layer spans a **fleet** that spreads the hardware load: today **two symmetric machines**, a laptop and a desktop running Linux under Windows. Another machine or a VPS joins through the same guided setup, without redesigning anything. Each machine can orchestrate and execute; there is no worker role. Work on a ticket gets its own isolated workspace, a git worktree with its own dev-server port derived from the branch name, so several agents work in parallel on tickets, reviews and ports to other release lines, on whichever machine the developer is sitting at.

The state of the work (ticket metadata, ledgers, memory, knowledge) is a git replica with a custom merge driver that merges the JSON per key. A conflict on the same field with different values is a hard stop, because it means the same work is running twice. The configuration is a chezmoi profile, pull-based, so there is no master machine; the two talk over a private Tailscale network. When memory runs short, a memory governor pauses the youngest batch job: full memory slows the work and never kills it.

<Note>
  <strong>Honestly:</strong> the fleet is my personal setup, verified end-to-end in both directions on real tickets. It is not a team standard. The team default is worktrunk on one machine, and the flow works there without any fleet at all.
</Note>
