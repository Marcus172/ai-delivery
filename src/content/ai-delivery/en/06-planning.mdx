### Decision maps

Work that does not fit in one session gets a **map** (the Wayfinder skill from an open-source set): a destination, standing notes and a glossary, the decisions so far, what is not yet specified, and what is out of scope. Under the map sit decision tickets, one per open question, settled one at a time, usually in a session where the agent questions me rather than codes. The rule is *plan, don't do*: a map produces decisions, not code. The tracker is plain markdown in the git-replicated state, so a map travels between machines and the glossary keeps agents and people on the same words.

### Visual plans and recaps, fully local

A spec is reviewed as an interactive **visual plan** (Agent-Native): diagrams, file maps, annotated code, open questions, sometimes a clickable prototype. A **recap** does the same for a finished change, for a reviewer or a tester. The person answers and comments inside the plan; the agent reads the feedback. It is the flow's formal spec format, not a markdown file.

Everything runs locally. A hosted validator would receive the client's screens, code and texts, so there is one central app per machine, plans live outside any git checkout, and the second machine reaches them over the private network. The risk is concrete: without an explicit local address, the plan verifier sends the whole plan to the hosted service. A rule, a preflight script and a check in the setup diagnostics make sure it always gets one.

<div class="example">
  <span class="k">Example, anonymised</span>
  <p>Triage of a reported problem found three defects in one screen. The agent presented a visual plan with three remedies, A, B and C, with the trade-offs of each. A person chose C. The same day: implementation, three rounds of review, a draft pull request.</p>
  <p>The agent never picks the direction of a fix on its own. It prepares the choice; the choice is made by a person, over a visual that shows what each option changes.</p>
</div>

<Note>
  <strong>The grill gate.</strong> An optional gate in the contract: before implementing, the agent questions the person on the brief until the open points are closed, and writes the decisions into the ticket metadata and the pull-request description. Finalising stops on an unconfirmed grill; it can only be skipped explicitly. It exists because of a risk I named early: delivering software without understanding the product, the brief or the impact.
</Note>
