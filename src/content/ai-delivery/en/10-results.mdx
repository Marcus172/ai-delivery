### Read this first

Two cohorts: the six months before the change and the five months after it, with the transition month left out. Same product, same repository, same tracker. Before reading the figures:

<ul class="caveats" data-caveats>

  <li><strong>Lead time is partly status discipline.</strong> After a merge the flow sets the ready-for-test state itself; before, a developer did it by hand, sometimes late. The In Progress to pull request figure is sturdier, because that state was always set by hand.</li>
  <li><strong>Lead time and returns from test are medium reliability.</strong> The project mix changed between the cohorts; the direction holds when the comparison is restricted to the one project present in both, but the after sample there is small.</li>
  <li><strong>The context diet regrew.</strong> The always-loaded instructions went from 57.6 KB to 7 KB and have since grown back to about 28 KB as release and tracker knowledge was added. The probes check that the knowledge stays reachable; the size is a budget I keep spending.</li>
</ul>

### Measured, before and after

<ResultsGrid locale={locale} />

Two of these are process measures, not quality measures: structured test notes show that the handover format is used, and multi-line delivery rose partly because more release lines ran in parallel. The quality signal is the share of tickets returned from testing (21 % → 11 %); the time from In Progress to pull request (−70 %) is a speed measure, and the sturdiest one here.
