## The brief: "it feels off", no examples

The product had thousands of strings written over years by developers, analysts, translators and the client's own people, in several places with no single gate between them. The client's brand rules existed, but they had been written for other channels, letters and a mobile app, and nobody checked the product against them. So I started with an inventory instead of fixes: over 150 terms with more than one translation, the support contact under six different names, the same generic error in about thirty wordings. The vague complaint became a measurable one.

## A persona that a person and an agent both read

Not a prompt that says "write like the brand". A data model, versioned in git:

- **Two layers.** A shared language base (typography, inflected variables, message and button grammar, channel limits such as SMS encoding) and the brand persona on top (voice, tone by situation, address, glossary, exceptions). The persona may override a base rule, by rule id.
- **Rules with a stable id**, a type (mechanical or judgment), a severity, a source (a chapter of the client's own document, or "our proposal") and a before/after example. Mechanical rules carry their own check and may block; judgment rules only advise.
- **A glossary** of preferred, allowed and banned terms; **recorded exceptions** (rule, string, reason, who approved); and **recorded conflicts** where the client's own rules contradict each other, each with a proposal for the client to decide.

The voice is translated, not invented: the persona converts the client's documents into rules and fills only the gaps. Anyone, including an agent, may propose a change to it; a person approves, and the agent never edits the persona itself. Mechanism and data are separate, so a second brand is a second data folder, not a rewrite.

## The audit pipeline

A repeatable run takes the strings from one fixed commit and produces one file of findings, each with a rule id, a proposed fix and a confidence. The model is chosen per task: a small one classifies the kind of each string, a mid-sized one applies the judgment rules in parallel batches, the deterministic checker applies the mechanical ones, and the largest model is the last sieve before a person: it keeps, edits or rejects every finding and merges proposals for the same string. Deterministic wrappers validate every model output against a schema; a bad batch is re-run, never patched by hand.

The verification step is not decoration: about a fifth of the raw findings did not survive it, and a further share had its proposal rewritten. A second run gets the previous one as input and carries over everything that did not change, so the client is asked again only about findings marked new or changed. Roughly half of the proposals come from mechanical rules, half from judgment.

## Every string photographed where it appears

A reviewer should approve a sentence where a customer will see it, not in a spreadsheet row. The product runs against a mock server with invented data in a trace mode where every rendered string carries its key. Browser agents receive a batch of keys, reach the state where each one appears, a failed request, a toast, a modal, an empty state, a form step, and take a screenshot with the string framed. Most strings only appear in edge states, so the agents stub API responses more often than they click. Screenshot quality is checked by machine: a string under a blurred modal, a frame around part of a sentence, sharpness inside the frame. When a string cannot be rendered, the reason is written for a non-technical reader. A side effect: while photographing, the agents found real product defects, which were fixed first.

## The review document closes the loop

One self-contained HTML file for a non-technical reader. It goes out by email or to a shared drive: no server, no install, no login. Changes sit in three parts by what is asked of the client: **(a) by your own rules** (confirm), **(b) our proposals** where the rules are silent (approve), **(c) conflicts in your rules** (decide).

How the reviewer works with it:

- **By rule, then by string.** Inside each part the changes are grouped by rule. A rule shows where it comes from in the client's own document, a before/after example and how many of its strings are decided.
- **Every occurrence in context.** A row shows where the string appears, a screenshot with the string framed (full size on click), today's wording, the proposal with the difference highlighted, and why.
- **One string or the whole rule.** Approve, disagree, or edit with your own wording, with an optional comment. A rule can be settled at once: approve all, disagree with the rule, approve the remaining.
- **A note on the rule itself.** When the rule is the problem, not the string, "propose a rule change" in its header takes a note on the rule as a whole.
- **Finding your way.** Search across texts and keys, filter by part and by state; from the second round on, new and changed findings are marked.
- **Nothing to lose.** Decisions are saved in the browser as you go. Export writes one file to send back, and loading an exported file opens the work again.

The returned file closes the loop. The pipeline first checks it against the run the document came from: the same set of findings, every decision paired with a finding, variables kept in edited texts, and contradictory decisions listed. Then it writes approved and edited strings back to the sources by key, without reformatting the file and skipping any key whose text changed in the meantime, opens one pull request per rule group, and turns rejected findings into exceptions in the persona and rule notes into proposed rule changes, which a person approves. In the next round the previous decisions are filled in, and rejected findings are not raised again.

## Part of everyday development, not a one-off audit

The persona ships as a plugin in the team's <a href={localizedPath(locale, "ai-delivery", "enablement")}>marketplace</a>, so every agent in the delivery flow has it wherever text is written or checked: building the UI and the back-end, checking an analysis or the client's brief, reviewing a Figma design. New strings follow the rules from the start, so the flow should not bring in new errors. The audit stays as a separate run: once per release it checks the application as a whole.

It also reaches past this codebase. The text a customer reads comes from other suppliers too, the mobile app, the sign-in (OIDC) provider, the client's website and more, and the audit takes them in as sources. The brand is checked where the customer reads it, not only where we write it.

## What AI made affordable

1. **Nobody owned the copy.** Without AI the project would have stalled, or produced one more style guide that nobody enforces.
2. **Judgment in a non-English language at volume.** Ordinary linters handle this language with regular expressions and a word list. Tone, clarity and "what happened and what to do" across thousands of strings and dozens of rules is well over a hundred thousand string-by-rule decisions, which no person makes consistently.
3. **Context for every string.** Finding the state where one error message appears is tens of minutes of a tester's time; the agents did it for hundreds of keys.
4. **Repeatability.** Every change of the persona or the code is a new run that recomputes only what changed. A manual audit is one snapshot, stale by the next release.
5. **People only approve.** Nobody writes from scratch; the human work of the whole phase was planned at roughly ten person-days, an estimate, while the agents ran in parallel. From an empty folder to the complete document with screenshots took about four weeks, alongside normal delivery.
