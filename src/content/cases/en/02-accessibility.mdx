## Thousands of marks, eighteen defects

The audit matrix covered every page in two languages and two themes, and marked a criterion as failing per page. Nothing pointed at an element. Read as data, the matrix had a clear shape: most failing criteria failed on almost every page, so the defect sat in a shared component, not on the page. The strategy followed from that: fix the component, and the test that proves it fixed, instead of working through the marks one by one.

## A manifest with a state machine

Each systemic criterion and each page-level finding lives in a machine-readable manifest with a schema and a lifecycle. The states are not decoration: *passing* means an automated test is green, *done* means a person confirmed it with a screen reader.

<A11yLifecycle locale={locale} />

<Glance locale={locale} label="How the evidence is kept">
  <Point locale={locale} title="Our own baseline, not the vendor's list">
    An axe scan of our own test environment stores an element-level baseline. It may only shrink, and every entry names the criterion it is there for.
  </Point>
  <Point locale={locale} title="Two levels, one audit trail">
    One entry per systemic criterion, one per page and criterion. A running note records every retest: what was found, how it was verified, which test holds it.
  </Point>
  <Point locale={locale} title="Progress per criterion">
    Not thousands of marks falling to zero. One ticket per audit and one per fix, never one per finding.
  </Point>
  <Point locale={locale} title="New scope without a reset">
    When the client's analyst widened the scope in September, the manifest took the new rows in without starting over.
  </Point>
</Glance>

<Detail locale={locale} label="The manifest in detail">

The criteria file holds, per systemic criterion, its level, the smallest set of libraries that own the fix, the pull request that fixed it, the regression tests that pin it, the next action and the running note. The findings file holds one entry per page and criterion. Both have a JSON schema.

The vendor's report decides priorities and stays as the audit trail; the tests are built from our own baseline, because only the baseline points at an element. A baseline is not an allowlist: it is committed, any new violation fails, and nothing sits in it unexplained.

<Facts label="Commands on the manifest">
  <Fact k="Status">The state per criterion and per ticket, with the owning libraries and the fixing pull request.</Fact>
  <Fact k="Next">Proposes the next item from the next action recorded on each entry.</Fact>
  <Fact k="Export">Publishes the state as a page for management and stakeholders, idempotently.</Fact>
  <Fact k="New audit">Bootstraps a new audit, and absorbs a re-scoped one without a reset.</Fact>
</Facts>

</Detail>

## Three agents, each with a narrow role

<A11yAgents locale={locale} />

One merged regression suite serves every audit: the tests live next to the code, and the audit is only metadata in their first line. When a future audit flags the same problem, an existing test is already red.

<Note>
  <strong>Deliberately not built:</strong> an agent that fixes accessibility defects on its own. A fix depends on context; the leverage is in triage and in tests, and automatic fixes invite regressions.
</Note>

## Six layers, one of them human

<TestPyramid locale={locale} />

<Stat id="a11y-specs" locale={locale} />

Automated checks catch perhaps a third of real barriers, and the documentation says so. Six of the systemic criteria are purely visual, focus rings, contrast in context, reflow, which is why the fifth layer exists: the vision audit, with calibrated examples, and a person reviews what it flags. The sixth layer is the only path to *done*: a person with a screen reader. No agent moves a finding there.

<div class="example">
  <span class="k">Example finding, fictional brand (Ferrylane)</span>
  <p>Criterion 2.4.7, focus visible. The primary button on the Ferrylane crossing picker lost its focus ring after a style change: the outline was set on a wrapper the keyboard never reaches. The fix landed in the shared button, the component spec asserts a visible outline on focus, the journey test tabs to the button for real, and a person confirmed it with a screen reader before the finding moved to done.</p>
</div>

<Detail locale={locale} label="The rules, for people and agents alike">

- No skipped test and no axe exclusion without the WCAG id and a reason next to it.
- No suppressed accessibility lint rule without the WCAG id, inline, never for a whole file.
- Never hide a focusable element from assistive technology: it hides the defect and creates a worse one.
- Axe-clean is not accessible: the visual criteria go to the vision audit, critical flows to a person.
- No per-page workaround for a systemic criterion: the fix belongs in the shared component.
- A chart whose data appears only on hover gets a text alternative, a data table that a screen reader reads.

</Detail>

## The tests are tested too

<Glance locale={locale} label="A test that cannot fail proves nothing">
  <Point locale={locale} title="Checked against a broken copy">
    The focus-trap specs run with the real library, not a mock. With the trap switched off, seven of eight tests turned red; with focus return removed, all three return tests did.
  </Point>
  <Point locale={locale} title="The layers check each other">
    A text search and the vision audit both passed reflow. A live sweep at 320 px found the root layout of every page wider than the screen; the fix went into the root, and a test pins it.
  </Point>
</Glance>

<div class="example">
  <span class="k">Example: one finding becomes a systemic fix, fictional brand (Ferrylane)</span>
  <p>A retest flagged one locked field in the Ferrylane booking-limits dialog: its "Not set" hint was visible, but a screen reader never read it. The fix for that field was one line, a description the field points to. The follow-up was the real fix. The shared form wrapper renders every hint under a predictable id and promises, in its own comment, that the input points to it, but only one field type had ever wired it. Ten other field types and the select had the same gap. All of them were wired in one pull request, one spec now checks the hint against every field type, and a person confirmed the original field with a screen reader.</p>
</div>

## Why this was not possible without AI

1. **Reading the matrix as data.** Thousands of marks across about 130 pages in four variants, mapped to the libraries that own each fix in one triage run, as a diff a person reviews, instead of days of spreadsheet work.
2. **Tests at volume, by the conventions.** Close to two hundred specs, each next to its code and each tied back to its manifest entry, written by an agent that knows the conventions and may not touch production code.
3. **Eyes on every critical screen.** The visual criteria are checked on the critical routes at two sizes whenever needed, and progress is validated in-house instead of waiting for an external retest.
4. **People decide.** Every change of state, every verdict on a screenshot and every screen-reader pass stays with a person.
